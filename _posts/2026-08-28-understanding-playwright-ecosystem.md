做前端或网页自动化的人，大概率都接触过 Playwright。最近几年大家谈论它的语境却经常变动。有人在写业务系统的端到端测试，有人在终端里用它录制点击操作，还有人在给 Claude Desktop 或 Antigravity 这类 AI 客户端配置工具时，把 Playwright MCP 写进配置文件。

这三处提到的都是 Playwright，背后调用的也是同一套浏览器内核，面对的实际场景却各有分工。

## Playwright Test，给持续集成和回归测试用的执行器

最早让 Playwright 流行起来的组件是它的测试框架 Playwright Test。

写过网页端到端测试的人大多吃过等待超时的苦头。网络请求慢了一点，或者前端组件还没渲染出来，脚本就已经点上去了，导致测试莫名其妙挂掉。Playwright 内部做了自动等待机制，在点击或输入之前，会先确认元素是否可见、稳定并且可以交互。这让测试跑起来踏实很多。

这套框架是给开发者和自动化流水线准备的。测试脚本用 TypeScript、JavaScript 或 Python 写好，每次提交代码或者跑流水线时，一条 `npx playwright test` 命令在后台拉起多个独立的浏览器上下文并行运行，跑完直接给出可视化的测试报告。这里的主角是写好的固定代码，目标是确认已有的业务功能没有被改坏。

## Playwright CLI，把繁琐工作交给终端命令

除了手写脚本，Playwright 提供的命令行工具包 Playwright CLI 也承担了很多前期准备工作。

最省时间的工具是代码生成器。在终端执行 `npx playwright codegen https://example.com`，系统会弹出一个浏览器窗口。你在页面里点输入框、输入文字、点击跳转，旁边的辅助窗口会实时把你刚才的操作翻译成测试脚本。记不清那些深层元素选择器的时候，在页面上手动点一遍，就能拿到大半能用的代码。

除了录制脚本，命令行工具还负责管理不同内核的浏览器二进制包。执行 `npx playwright install` 就能把 Chromium、Firefox 和 WebKit 统一下载到本地。排查偶发失败时，通过 `show-trace` 打开录制好的轨迹文件，能逐帧查看当时的页面 DOM 状态、控制台日志和网络请求。这些命令把写测试和修测试过程里的繁琐动作接了过去。

## Playwright MCP，给 AI 智能体开的浏览器窗口

到了大语言模型和 AI Agent 普及以后，浏览器的使用方式又延伸出一种新形态。大模型本身只接收和输出文字，没办法直接看到网页长什么样，也碰不到页面上的输入框。

Playwright MCP 顺着这个问题做了一层封装。它遵循 Model Context Protocol 协议规范，把 Playwright 操控浏览器的能力拆解成一组标准工具。这些工具包括打开指定网址、点击指定位置、在输入框里打字、截取当前屏幕，以及在页面上下文中执行脚本。

把 Playwright MCP 接入 AI 客户端之后，智能体就拿到了操作真实浏览器的能力。比如让它去某个系统里核对数据，或者在本地帮开发者调试页面布局，它会根据当前目标自行决定先访问哪个链接、截图查看视觉效果、点击哪些按钮。这里不需要人类预先写死执行步骤，操作浏览器的决策过程交给了模型。

## 三样工具怎样各司其职

把这三个部分放在一起看，分工很容易理清。

开发者在本地想快速写出用例，可以用命令行工具录制和调试。整理好的测试代码交给测试框架，放进持续集成流水线里定时回归。如果遇到需要自主探索页面、抓取动态内容或者由 AI 协助排查问题的任务，再通过协议接口把浏览器开放给智能体。

同一套浏览器自动化能力，在不同的使用场景里提供了趁手的接口，选准了能给日常开发省下不少力气。
