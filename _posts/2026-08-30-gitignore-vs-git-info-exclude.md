用 Git 管理代码时，大家最熟悉的忽略配置肯定是根目录下的 `.gitignore`。

每次构建工具生成了一堆编译产物，或者测试脚本吐出一堆临时日志，顺手往 `.gitignore` 里添上一行，已经成了很多人的肌肉记忆。

但在 `.git` 目录深处，其实还藏着一个叫 `info/exclude` 的文件。它和 `.gitignore` 遵循完全一致的匹配规则，日常却很少被人提起。

这两个文件到底该怎么选，它们在平时的协作里各自适合放什么内容？

## 规则完全相同，归宿截然不同

从匹配语法来看，这两个文件没有任何差别。

通配符、目录斜杠、感叹号取反，在 `.gitignore` 里怎么写，搬到 `.git/info/exclude` 里就能怎么用。

区别全在它们的位置与归宿上。

`.gitignore` 放在工作区里，属于代码仓库的一部分。你修改了它，就必须提交进版本库，推送到远端之后，克隆仓库的每位同事、CI 自动化流水线以及部署服务器，都会立刻遵循这套规则。

`.git/info/exclude` 躲在 `.git` 这个隐藏文件夹内部。Git 的版本控制只管工作区里的文件，根本不会追踪 `.git` 目录本身的变动。

写进 `info/exclude` 的规则只在当前这台电脑的这一个本地目录生效。你既推不上去，别人也拉不下来，完全是一份属于你个人的私有忽略清单。

## 什么时候该用 .gitignore

只要某种文件是整个团队在开发、测试或部署时都会普遍生成的，就应该大大方方写进 `.gitignore`。

最典型的有这么几类。

第一类是语言和构建工具的生成物。Java 项目里的 `target/`，Node 项目里的 `node_modules/`，Python 项目里的 `__pycache__/`，还有静态博客生成的 `_site/`。任何拉下代码准备干活的人，电脑里都会产生这些目录。

第二类是通用的工具与环境配置。团队统一使用的编辑器格式配置、公共测试框架输出的覆盖率报告，或者像自动化测试工具自动落下的 `.playwright-mcp/` 截图目录。

把这些规则放进公共的 `.gitignore`，能帮整个团队统一防线，省得每个人都在本地重复配置一遍。

## 什么时候该用 info/exclude

如果在日常开发里，你有一些只属于你个人的临时文件，而且你不想动项目的公共配置文件，`info/exclude` 就是最舒服的选择。

很多开发者在排查 Bug 时，喜欢在项目根目录下随手扔一个临时脚本，比如 `scratch.py` 或者 `debug.json`。这些文件只为了辅助你当下的调试，跟业务代码毫无关系。

要是把 `scratch.py` 随手写进 `.gitignore`，你提交代码时就会把这条私人规则带进公共仓库。别人拉下更新，看到项目规则里多出一些奇奇怪怪的个人文件名，难免一头雾水。

这时候直接把文件名追加到 `.git/info/exclude` 即可。

本地的代码树干干净净，`git status` 不会跳出未跟踪提示，公共的 `.gitignore` 也不用被临时内容打扰。

还有一种常见情况是本地个性化的配置覆盖。有时候你需要在本地调试一套特殊的端口或本地数据库地址，改了本地的某个私有配置文件。只要把那个特定文件名放进 `info/exclude`，就能安心在本地做实验，不用担心 `git add .` 的时候误把它送进暂存区。

## 全局忽略也是一种补充

除了这两个针对单一仓库的文件，Git 还提供了全局忽略机制。

如果你有一些系统级的扰乱文件，比如 macOS 随处生成的 `.DS_Store`、Windows 缩略图 `Thumbs.db`，或者你个人偏好的编辑器缓存目录，最省心的办法是配置全局忽略文件。

通过命令指定一个像 `~/.gitignore_global` 这样的路径，里面的规则会对你电脑上的所有 Git 项目同时生效。

```bash
git config --global core.excludesfile ~/.gitignore_global
```

把操作系统和个人编辑器的杂质交给全局规则处理，把团队通用的构建产物留给 `.gitignore`，再把当下临时调试的私有文件塞进 `info/exclude`。

分清这几层位置，日常提交时工作区就会始终保持清爽。
